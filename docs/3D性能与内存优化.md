## 1. 结论速览

| 指标 | 优化前 | 优化后 | 变化 |
| --- | --- | --- | --- |
| 场景静态三角形 | 2697 万 | 339 万 | **-87%** |
| 实测帧率（花园内，M 系 16G） | 20.6 FPS | 60 FPS（vsync 打满） | ×2.9 |
| 每帧渲染三角形（含阴影/后处理多 pass） | — | 约 510 万 | — |
| 帧时间 | ~48 ms | 16.12 ms | — |
| 园林资产单件 GLB | 40~70 MB | 1~4 MB | -95% |
| 园林资产目录（含压缩版与 scene.json） | 1.2 GB | 47 MB | -96% |
| 单件贴图 | 31.5 MB（3×4096² PNG） | 0.3 MB（1024² JPEG） | -99% |
| 单件面数 | 约 50 万 | 2.5 万~7.2 万 | -90% 以上 |

三条核心结论：

1. **性能损失的大头是顶点吞吐**（高模 + 阴影 pass 双份渲染），不是分辨率或后处理。实测定位：关闭阴影 FPS +128%，pixelRatio 2→1 与移除 DOF 各只占约 +14~15%；
2. **正确姿势是资产离线降级**（减面 + 压图），而不是运行时补偿；
3. **内存压力同样致命**：4096² 贴图解码后约 192 MB/件，21 件近 4 GB，统一内存机器直接扛不住（详见第 7 节账本）。

## 2. 原版优化体系（混元模型引入前的基线）

### 2.1 根基：美术风格即优化策略

原版"满屏细节还流畅"的第一层原因是美术方向本身：低多边形模型 + 全场景共用一张调色板纹理（`palette.ktx`，`Materials.createPalette`）+ 程序化天空/水面。没有高精度贴图、真实反射、百万面资产——把资产的基础代价压到极低，再叠加后续各层工程优化。

### 2.2 资产管线：构建期离线压缩

`scripts/compress.js`（`npm run compress`）在构建期完成：

- **GLB 几何 Draco 压缩**：`edgebreaker` 方法，量化 position 12bit / normal 6bit / texcoord 6bit / color 2bit；
- **纹理 KTX2 压缩**（toktx）：默认 `etc1s q255`，按路径使用专用 preset（如 uastc、`genmipmap`），单通道纹理 `--swizzle r001` 只传 R 通道，省 3/4 带宽；
- **UI 图片转 WebP**（sharp q80）；
- 运行时由 `DRACOLoader`（`preload()`）+ `KTX2Loader`（`setTranscoderPath('./basis/')` + `detectSupport`）解码（`ResourcesLoader.js`）。

### 2.3 渲染管线：WebGPU + 分辨率与视锥控制

- **Three.js WebGPURenderer + TSL 节点材质**（`Rendering.js` setRenderer）：`powerPreference: 'high-performance'`，antialias 仅在 `pixelRatio < 2` 时开启；
- **pixelRatio 上限 1.5**（`Viewport.js` `pixelRatioMax`）——高 DPI 屏不渲染全分辨率，单点收益最大的优化之一；
- **相机 fov 25 / near 0.1 / far 200**（`View.js` setCameras）——视锥紧凑；
- `sortObjects = false` + `setOpaqueSort` / `setTransparentSort` 按 renderOrder 自定义排序，砍掉每帧全量排序开销；
- 关键资源在 `index.html` 直接 `<link rel="preload">`（palette.ktx、respawns 等 4 项）。

### 2.4 后处理与阴影：全部可分级

- **Bloom 按质量分级**：mip 链高质量 5 / 低质量 2，threshold 1、strength 0.25（`Rendering.js` setPostprocessing）；
- **cheapDOF**（自制廉价景深，`Passes/cheapDOF.js`）：低质量时直接 `scenePassColor.add(bloomPass)` 绕过；
- **水面**（`World/WaterSurface.js`）：单个 `PlaneGeometry(1,1,1,1)`，波浪在 shader 里算，倒影用 `hashBlur(screenUV)` 屏幕空间模糊假反射——不做真实反射渲染；
- **阴影**（`Ligthing.js`）：仅一盏方向光；shadow map 1536/512 分级；阴影相机范围随玩家 `view.optimalArea.radius` 动态跟随，而不是覆盖整个场景；normalBias 0.1 / bias -0.001 调优。

### 2.5 核心手法：把逐帧计算搬进 GPU

| 对象 | 规模 | 实现方式 |
| --- | --- | --- |
| 草（`Grass.js`） | 78,400 根 | **单个 mesh**，顶点只存 xz 坐标，形状/弯曲/风全部 TSL 顶点着色器生成 |
| 树叶（`Leaves.js`） | 2^7~2^11 片 | `instancedArray` 位置/速度缓冲 + TSL 在 GPU 上模拟物理 |
| 雨（`RainLines.js`） | 2^11 条 | GPU 动画线段 |
| 雪 / 闪电粒子 / 萤火虫 | 各自批量 | 小段数几何（如 `CircleGeometry(0.015, 8)`）+ 实例属性 + TSL |
| 天空（`Fog.js`） | 全屏 | 程序化 `backgroundNode` 渐变，**无天空盒纹理**；雾在 shader 里算 |

CPU 侧无逐帧粒子计算——这是原版即使在低端设备也流畅的关键。

### 2.6 实例化、物理与质量分级

- **`InstancedGroup.js` 覆盖 9+ 类对象**：灯柱、灯笼、砖块、长椅、栅栏、爆炸箱、饼干、保龄球瓶、风扇等；且惰性更新——只有 `needsUpdate` 的实例才重写 instanceMatrix；
- **物理（Rapier WASM）**：碰撞体只用 cuboid/ball/cylinder 简化形状；fixed 物体 `sleeping: true` 预眠；角色/车辆未激活时 `body.setEnabled(false)`；
- **质量分级（`Quality.js`）**：移动端 UA 自动降至 level 1，Options 面板可切换 High/Low，事件驱动热切换；联动阴影贴图 / bloom mips / DOF / 水面模糊 / 粒子数量。

### 2.7 架构细节

- 15 阶段优先级 tick 调度（`Ticker.js`），保证依赖顺序、对象只在自己阶段更新；
- `threejs-override.js` 覆写 `Object3D.copy` 跳过 userData 深拷贝；
- `ResourcesLoader` 加载器单例 + 缓存 Map；Garden 资产懒加载；
- resize 双速响应：立即 setSize + 400 ms 防抖的 `throttleChange`（处理重建草几何等昂贵操作）。

## 3. 混元高模的性能冲击与瓶颈定位（2026-10-06 实测）

### 3.1 问题现象

园林由 **21 个唯一混元资产**（`scene.json` 中共 50 条摆放，同 key 复用同一 GLB）拼装。优化前的资产规格：**每件约 50 万三角形、3 张 4096² PNG 贴图**。

- 场景总量：**2697 万三角形**，每帧再乘 2（主画面 + 阴影贴图各渲一遍）；
- 实测：Mac M 系列 16G 上 **20.6 FPS**，鼠标事件明显卡顿发涩。

### 3.2 瓶颈定位：对照实验

不猜，逐项开关做对照（同一相机位、同一场景状态）：

| 对照项 | FPS | 变化 | 判定 |
| --- | --- | --- | --- |
| 基线 | 20.6 | — | — |
| **关闭阴影** | 47 | **+128%** | 最大瓶颈（顶点吞吐双份） |
| pixelRatio 2→1 | — | +14% | 次要 |
| 移除 DOF | — | +15% | 次要 |

结论：分辨率与后处理只是零头，**顶点吞吐是绝对大头**——阴影开启时顶点成本按 2 倍预算。

### 3.3 根因分析

1. **顶点吞吐**：AI 生成高模顶点数远超集显逐帧处理能力，且阴影 pass 完整重渲一遍主场景几何；
2. **统一内存压力**：4096² PNG 解码后 RGBA 约 64 MB/张 × 3 张 ≈ **192 MB/件**，21 件近 **4 GB**——16G 统一内存机器另一重打击（详见第 7 节）。

## 4. 修复一：资产级离线降级（`scripts/hunyuan/process.js`）

在规范化流水线中新增两步（位于尺寸归一化之后、碰撞体注入之前，减面后重新计算包围盒保证碰撞体贴合）：

### 4.1 减面（meshoptimizer）

```js
weld({ tolerance: 0.0001 })
simplify({ simplifier: MeshoptSimplifier, ratio: 0.05, error: 0.002, lockBorder: false })
```

- `weld` 先合并拆分顶点，提高简化质量；
- `ratio: 0.05` = 目标保留比例；`error: 0.002` = 相对模型半径的误差上限（过大可见形变，过小减不下去）；
- 效果：**50 万面 → 2.5 万面**（优化后单件实测 25k~72k 面）。

### 4.2 贴图压缩（sharp）

```js
compressTexture(texture, {
    encoder: sharp,
    targetFormat: metadata.hasAlpha ? 'png' : 'jpeg',
    resize: [ 1024, 1024 ],
    quality: 85
})
```

- 最大边长 1024²；无 alpha 转 **JPEG q85**，有 alpha 保留 PNG；
- 效果：单件贴图 **31.5 MB → 0.3 MB**。

### 4.3 参数覆盖机制

三级覆盖链，均可用：

```js
{ ...defaultSimplify, ...manifest.defaults.simplify, ...asset.simplify }
```

- 全局默认：`defaultSimplify = { ratio: 0.05, error: 0.002 }`、`defaultTexture = { resize: [1024,1024], quality: 85 }`；
- 资产级 `simplify` / `texture` 字段可覆盖参数，置 `false` 可整体禁用（如需要保留某个高精度核心摆件）。

### 4.4 产物与数据

- 21 个资产全部重跑：GLB **40~70 MB → 1~4 MB**；目录 **1.2 GB → 47 MB**（含 `-compressed` Draco 版，已全量重新生成）；
- `-compressed` 版 = 普通版再走 gltf-transform Draco（量化参数与 compress.js 一致），供运行时按 `VITE_COMPRESSED` 选用；
- 原始高模保留在 `resources/hunyuan-raw/`（1.1 GB，gitignore）；
- 重跑命令：

```bash
node scripts/hunyuan/process.js              # 全部资产
node scripts/hunyuan/process.js --only <key> --compress
npm run garden:build                         # 生成+处理一键串联
```

## 5. 修复二：运行时参数与物理微调

### 5.1 `Viewport.pixelRatioMax` 2 → 1.5

`Viewport.js` measure()：`Math.min(devicePixelRatio, 1.5)`。渲染像素量降约 44%，肉眼几乎无感。

### 5.2 `cheapDOF` repeats 25 → 12

`Passes/cheapDOF.js`：景深 hashBlur 的采样迭代减半，画面差异极小，开销显著下降。

### 5.3 阴影贴图 2048 → 1536

`Ligthing.js`：level 0 从 2048 降至 1536（level 1 维持 512）。阴影本就跟随 optimalArea 动态覆盖，1536 对画面影响很小。

### 5.4 物理：水下阻尼状态缓存

`Physics/Physics.js` update()：原实现每帧对**全部刚体**无条件 `setLinearDamping/setAngularDamping`——这是 WASM 跨界调用，刚体多时开销可观。改为 `physical.isDeep` 状态缓存，**仅在入水/出水切换时写入一次**。

## 6. 实测结果与验证方法

### 6.1 结果

- 出生点与花园内均 **60 FPS（打满 vsync）**，帧时间 **16.12 ms**；
- 每帧渲染三角形约 510 万（含阴影/后处理多 pass），场景静态三角形 339 万（-87%）；
- 截图目检：无破面、无贴图异常（aesthetic 层面减面质量可接受）。

### 6.2 验证流程（可复用）

1. 浏览器子代理打开 dev 页面；
2. 通过控制台调用 `physicalVehicle.moveTo()` 传送到目标取景位；
3. `requestAnimationFrame` 采样帧率 + 截图目检。

### 6.3 注意事项

- dev 模式下 `static/` 批量变更会触发 vite-plugin-restart 反复重启，重启窗口刷页会污染模块图——**验证前须硬刷新**（详见记忆库 2.2.3）；
- 对照实验必须固定相机位与场景状态，否则数据不可比。

## 7. 内存专题

### 7.1 贴图内存账本

GPU/统一内存占用按**解码后**计算，与文件体积无关：

| 规格 | 单张解码 RGBA | 单件（3 张） | 21 件 |
| --- | --- | --- | --- |
| 4096² PNG（优化前） | 4096×4096×4 B ≈ 64 MB | ≈ 192 MB | **≈ 4 GB** |
| 1024² JPEG（优化后） | 1024×1024×4 B ≈ 4 MB | ≈ 12 MB | ≈ 252 MB |

（mipmap 另加约 1/3；KTX2 走压缩纹理直传可更省，但混元资产当前为 JPEG 内嵌。）

**这就是"瘦身贴图"的真正意义**：不只是加载快，而是把常驻内存从 GB 级压回百 MB 级。

### 7.2 几何与加载内存

- 减面 -90%+ 直接削减顶点/索引缓冲占用；Draco 进一步减少**传输体积**；
- 目录 1.2 GB → 47 MB，配合懒加载（按 scene.json 唯一 key 去重请求）+ ResourcesLoader 缓存，加载峰值内存同步大幅下降。

## 8. 方法论沉淀（可复用）

### 8.1 瓶颈定位法

先测量再动手：逐项开关「阴影 / 分辨率 / 后处理」做对照实验，用数据排序瓶颈。本案顺序：顶点吞吐（+128%）>> 分辨率（+14%）≈ DOF（+15%）。

### 8.2 高模入库判定阈值

- 单资产 **> 10 万面**或单贴图 **> 2048²** → 先离线减面/压图再入库；
- **阴影开启时顶点预算按 2 倍计**。

### 8.3 适用边界

一切 AI 生成/扫描类高模资产（混元3D、TRELLIS、摄影测量）进入实时渲染项目；原则是**资产离线降级优先于运行时补偿**。
